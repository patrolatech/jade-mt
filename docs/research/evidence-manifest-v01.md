# EvidenceManifest v0.1 — review and closure

Estagiário 1 (Blockchain/Evidence), etapa 16–30 Set — Atividade 1.

## Question this closes

> Given an environmental opinion produced by the oracle, what is the minimal
> set of information we must preserve and record so that validation can be
> audited and verified later?

Priority: simplicity. No DID, Verifiable Credentials, SBT, Merkle tree or
multisig until this minimal core is validated.

## Source of truth

`EvidenceManifestV01Schema` — `packages/schemas/src/index.ts:95-152`
(TypeBox, not zod). It is treated as a starting point, not a final spec
(see the "provisional integration contract" comment at line 94).

Every property below is **required** unless marked optional; TypeBox models
"not applicable / not measured" via `T | null`, and this repo's schema never
uses that to mean "unknown validity" — see the engineering hypothesis in
`docs/research/open-questions.md:58` ("unknown manifest measurements use
null, never a fabricated zero").

### On-chain vs off-chain summary

On-chain today (`contracts/jade-attestation/src/lib.rs:27-34`, `Attestation`
struct): `validation_id`, `evidence_hash` (aggregate SHA-256 of the whole
manifest, computed by `@jade/evidence`, not a manifest field itself),
`methodology_version`, `result`, `validator`, `status`.

Everything else in the manifest — `geometryHash`, `commodity`, `cutoffDate`,
`sources[]`, `analysis.*` — stays **off-chain only**, covered transitively by
`evidence_hash`. Rationale: `sources[]` is unbounded in size and `commodity`
is business data; neither belongs in Soroban persistent storage. This is
consistent with `docs/architecture/environmental-flow.md`'s statement that
"the contract does not independently validate source truth, environmental
conclusions or legal compliance."

This table is a starting point for **Atividade 3**, not a final decision —
in particular, whether any off-chain summary field (e.g.
`analysis.intersectionAreaM2`) should instead be emitted as a Soroban
_event_ rather than staying purely off-chain is left for that activity to
evaluate, since it also depends on storage/TTL cost tradeoffs (Atividade 4).

## Candidate new fields

The task brief asks to evaluate whether `lotId`, a reference/storage URI,
`warnings`, and an implementation version are actually necessary — not to
add them by default.

| Candidate                                        | Decision                                     | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lotId`                                          | **Do not add**                               | No system in this repo currently models a "lot"/land-parcel entity distinct from `validationId` + `input.geometryHash`. Adding it now would be speculative. Left as an open question for the API/product owner: is there an external land-registry id validations must anchor to?                                                                                                                                                                                                                                                                                    |
| Reference/storage URI (`evidenceUri`)            | **Add** — optional, nullable, off-chain only | Without it, hashes are cryptographically verifiable but not practically auditable: nothing in the manifest says where to retrieve the original geometry/source bytes that hash to `geometryHash`/`payloadHash`. This is the one concrete gap found. Nullable because an issuer may not always have retrievable public storage. Overlaps with the already-open question in `docs/research/open-questions.md:40` ("Should evidence initially use S3/MinIO or IPFS?") — the storage backend itself remains that question's scope; this field only reserves the pointer. |
| `warnings`                                       | **Do not add yet**                           | The distinction between a full `INCONCLUSIVE`/`ERROR` result and a "degraded but still decisive" result is still an open joint decision (`docs/methodology/JADE-ENV-0.1.md`, decision-rule section; `docs/research/open-questions.md:23`). Adding a `warnings` shape now would preempt that decision. Left as an open question.                                                                                                                                                                                                                                      |
| Implementation version (`implementationVersion`) | **Add** — optional, nullable, off-chain only | Distinguishes the version of the _oracle/evidence codebase_ that produced the manifest from `schema` (manifest format) and `methodology.version` (scientific rule version). Low risk, useful for debugging and reproduction (e.g. tracing a miscalculation to a specific code version) without affecting on-chain footprint.                                                                                                                                                                                                                                         |

## Schema change applied

`packages/schemas/src/index.ts`:

1. Added `evidenceUri?: string | null` and `implementationVersion?: string | null`
   to `EvidenceManifestV01Schema` (both `Type.Optional`, off-chain only, not
   referenced by the contract).
2. Aligned `input.commodity`'s constraints
   (`minLength: 1, maxLength: 100, pattern: '\\S'`) with
   `ValidationInputSchema.commodity`, which already carried those bounds —
   the manifest's copy had only `minLength: 1`, an inconsistency with no
   documented reason.

No fields were removed or made optional beyond the two additions above.

## Open questions carried forward

- `lotId`: does an external land-registry identifier need to be anchored in
  the manifest? (product/API decision, not blockchain-layer)
- `warnings`: structure and relationship to `INCONCLUSIVE`/`ERROR`, blocked
  on the joint decision-rule mapping in `docs/methodology/JADE-ENV-0.1.md`
- Storage backend for `evidenceUri` (S3/MinIO vs IPFS) —
  `docs/research/open-questions.md:40`, unchanged by this activity
- Which off-chain fields, if any, should become Soroban events rather than
  staying purely off-chain — deferred to Atividade 3

## Expected result

A single v0.1 evidence model usable by the backend, the hashing layer
(`@jade/evidence`), and the contract (`contracts/jade-attestation`) — closed
except for the two open questions above, which are explicitly out of this
activity's scope (product decision, and a joint methodology decision).
